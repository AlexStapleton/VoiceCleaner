# Low-latency, glitch-free real-time audio pipelines on Windows 10/11 (for VoiceCleaner)

Scope: what Microsoft and other references recommend for a capture -> process -> "virtual mic" pipeline, and what VoiceCleaner (WASAPI shared + event-driven, 480-sample framer, SPSC rings, PI-controlled Catmull-Rom drift resampler, VB-Cable output) could change. Sources were fetched in October 2026. learn.microsoft.com pages were read in full through curl. The vb-audio.com forum could not be fetched directly (DNS failure from the fetch tool), so VB-Cable forum statements come from search-result excerpts and are labeled as such.

## 1. IAudioClient3 / low-latency shared mode, and exclusive-mode trade-offs

### Takeaway
On Windows 10 and later, `IAudioClient3::InitializeSharedAudioStream` can run a shared-mode stream below the default ~10 ms period. This only works if the endpoint's driver declares small-buffer support. The inbox HDAudio driver supports 128-480 frames at 48 kHz. Many third-party and virtual drivers (VB-Cable is unverified) report only the default period. When one client asks for a small period, every client on that endpoint and mode switches to it, and the engine can be "locked" at another client's period. Exclusive mode removes the engine, but it blocks every other app from using the device, so it is a poor fit for the physical mic and does not apply to a virtual cable that other apps must open.

### Cited Findings
- Windows 10 cut audio-engine latency to about 1.3 ms on render (from about 12 ms float / 6 ms int before Windows 10) and to about 0 ms on capture. Before Windows 10 the driver/engine buffer was always about 10 ms; from Windows 10 on, the driver defines it. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- `IAudioClient3` adds `GetCurrentSharedModeEnginePeriod`, `GetSharedModeEnginePeriod` (returns default, fundamental, min and max period) and `InitializeSharedAudioStream`. Legal periods are multiples of the fundamental period between min and max. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- If another client already runs the engine at a different period, `InitializeSharedAudioStream` returns `AUDCLNT_E_ENGINE_PERIODICITY_LOCKED`; for a format clash it returns `AUDCLNT_E_ENGINE_FORMAT_LOCKED`. An invalid period returns `AUDCLNT_E_INVALID_DEVICE_PERIOD`. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio); [MS Learn: InitializeSharedAudioStream](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)
- Example values from the docs at 44.1 kHz: default 448 frames, fundamental 4, min 48, max 448. With `InitializeSharedAudioStream` you can't choose a buffer size; it is derived from the period. — [MS Learn: InitializeSharedAudioStream](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)
- Driver requirement: the driver must declare its minimum buffer size per mode through `DEVPKEY_KsAudio_PacketSize_Constraints2` (Windows 10 1607+). It should also implement `IMiniportWaveRTInputStream/OutputStream` packet/position DDIs and register its interrupts and threads with PortCls (`PcAddStreamResource`). Without updated drivers, systems stay at 10 ms. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- The inbox HDAudio driver supports buffers from 128 samples (2.66 ms at 48 kHz) to 480 samples (10 ms). — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- By default all apps use 10 ms buffers. Once one app requests small buffers, all apps on the same endpoint and mode switch to that size until it exits. Small buffers raise power use because the CPU wakes more often. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- Below a threshold buffer size, Windows enters a special mode that protects audio resources. That protection covers only the engine thread, driver-registered resources, and app work items submitted through the Real-Time Work Queue API (`RtwqLockSharedWorkQueue(L"Audio"/"ProAudio")`) or MF work queues tagged Audio/ProAudio. Microsoft recommends these over app-owned threads. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- `AUDCLNT_STREAMOPTIONS_RAW` bypasses OEM signal processing (APOs), which can lower latency. `AUDCLNT_STREAMOPTIONS_MATCH_FORMAT` avoids engine resampling. Raw is allowed only if `System.Devices.AudioDevice.RawProcessingSupported` is true. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio); [MS Learn: Audio signal processing modes](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/audio-signal-processing-modes)
- Raw capture must not include adaptive processing such as echo control, AGC or noise suppression; only linear EQ is allowed. — [MS Learn: Audio signal processing modes](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/audio-signal-processing-modes)
- In exclusive mode the data bypasses the engine, but no other application can use that endpoint. ASIO also relies on exclusive access. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- AudioGraph adds one buffer of capture latency, plus another render buffer when buffers are over 6 ms. WASAPI is the lower-latency choice. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)

### Inferences
- Concrete change: open capture through `IAudioClient3`, call `GetSharedModeEnginePeriod` for the 48 kHz float mix format, and request the smallest legal period, for example 128 or 240 frames. Fall back to `Initialize` when the call returns `E_NOINTERFACE`, `AUDCLNT_E_ENGINE_PERIODICITY_LOCKED`, or reports min == default. Do the same on the VB-Cable render side, which will most likely report only 480.
- The 480-sample framer then becomes the latency floor: with a 128-frame capture period the framer waits for 3.75 periods. If the DSP (for example a 10 ms-hop denoiser) truly needs 480-sample blocks, the gain from small capture periods is smaller, roughly at most 10 ms minus one small period of scheduling slack. Pushing smaller hops into the DSP is the bigger lever.
- Consider `AUDCLNT_STREAMOPTIONS_RAW` on capture when it is supported. VoiceCleaner does its own denoising, so OEM noise suppression and AGC are redundant, add latency, and can fight the app's DSP.
- Do not use exclusive mode on the physical mic by default; it would silence the mic for every other app. Expose it at most as an "advanced" option.

### Gaps
- No published measurement was found of the period VB-Cable reports through `GetSharedModeEnginePeriod`. Logging this at runtime on user machines would answer it.
- No current Microsoft figure was found for the default/minimum engine periods typical of USB Audio Class 2 (usbaudio2.sys) devices.

## 2. Virtual cable latency vs. custom driver vs. APO

### Takeaway
VB-Cable's internal buffer defaults to 7168 samples. VB-Audio staff say a stream uses about half of it, which is up to about 70 ms at 48 kHz. Staff advise against lowering it, while also giving a sizing rule of at least 3x the larger client buffer. Virtual Audio Cable (Muzychenko) exposes a 1-20 ms period and a "clock control" feature for drift. The lowest-latency, most deployable path is a self-owned virtual audio driver, either a SysVAD/MSVAD-derived PortCls driver or an ACX/KMDF driver, whose capture-endpoint period VoiceCleaner controls. That requires an EV certificate plus Microsoft attestation signing. Attestation-signed drivers aren't published on Windows Update but install fine by an installer. Capture-side APOs ship only with a driver package, need HLK compliance on Windows 11, and are for OEM/IHV scenarios, so they are a poor fit for an indie app.

### Cited Findings
- VB-Cable: the control panel's "max latency" is in samples, from 512 to 7168. Staff say the default 7168 samples gives a 150 ms buffer at 48 kHz, a stream can use only about half of it ("you cannot get more than 70 ms delay with VB-CABLE"), and "a latency max of 2048 / 2 samples = 21.3 ms at 48 kHz". Staff give the rule "VB-CABLE internal latency should be >= 3x (MAX (PS,RS))", meaning 3x the larger of the player and recorder buffer. They advise against lowering the value: setting 1536 "can create other problems and won't change anything on your overall latency". These are search-result excerpts from the forum; direct fetch failed. — [VB-Audio forum p=6289](https://forum.vb-audio.com/viewtopic.php?p=6289); [VB-Audio forum p=473](https://forum.vb-audio.com/viewtopic.php?p=473); [VB-Audio forum p=1594](https://forum.vb-audio.com/viewtopic.php?p=1594)
- VB-Cable driver pack 45 is dated October 2024 and covers XP to Win11, including Arm64. It is donationware. VB-Audio Hi-Fi Cable must use the same sample rate on input and output and is bit-perfect. — [vb-audio.com/Cable](https://vb-audio.com/Cable/)
- Virtual Audio Cable (Muzychenko): the interrupt period is configurable from 1 to 20 ms per a FlexRadio guide, which is a secondary source. Audio Repeater offers MME and Kernel Streaming versions. When one endpoint belongs to VAC, "you can turn on VAC clock control to eliminate clock rate difference problems"; only one side can use clock control at a time. — [FlexRadio help](https://helpdesk.flexradio.com/hc/en-us/articles/206605196-How-to-Setup-Virtual-Audio-Cable-VAC-4-0x-with-PowerSDR); [VAC manual: Audio Repeater](https://vac.muzychenko.net/en/manual/repeater.htm)
- Users report stutter on VAC's MME path below about 200 ms. This is anecdotal. — [Adobe community](https://community.adobe.com/t5/audition-discussions/wasapi-and-virtual-cable/m-p/11715526)
- SysVAD is Microsoft's virtual audio device driver sample (source only, unsigned). It also contains the APO samples, including the AEC APO. Its source also shows how to declare `KSAUDIO_PACKETSIZE_CONSTRAINTS2`, the small-buffer support from section 1. — [MS Learn: Sample audio drivers](https://learn.microsoft.com/en-sg/WINDOWS-HARDWARE/DRIVERS/audio/sample-audio-drivers); [GitHub: Windows-driver-samples/audio/sysvad](https://github.com/microsoft/Windows-driver-samples/tree/main/audio/sysvad); [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- ACX (Audio Class eXtension) is a KMDF class extension for audio drivers. It supports only WaveRT streaming, coexists with PortCls drivers, and has samples at `Windows-driver-samples/audio/Acx/Samples`. Its stated goals include reducing third-party code and "no ... additional or noticeable latency". — [MS Learn: ACX overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/acx-audio-class-extensions-overview)
- Open-source precedent: Scream is an MSVAD-derived virtual sound device (MS-PL) that publishes signed x64/x86/arm64 builds for Windows 10. It is a render device that streams over the network. — [GitHub: duncanthrax/scream](https://github.com/duncanthrax/scream)
- Attestation signing requires the Hardware Developer Program and an EV code-signing certificate; you submit an EV-signed CAB in Partner Center and Microsoft re-signs it. "Attestation signed drivers that target retail audiences aren't published on Windows Update." — [MS Learn: Attestation signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation)
- APOs are in-process COM DLLs installed and registered through an INF, so they are part of a driver package. "APOs should not introduce significant latency into the audio processing chain." — [MS Learn: Implementing APOs](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/implementing-audio-processing-objects)
- New APOs shipping on a Windows 11 device must use the CAPX APIs (`IAudioSystemEffects3`, Settings, Notifications, Logging, Threading, AEC frameworks), validated by HLK. Using the registry instead of the Settings framework fails HLK. CAPX is available from build 22000 and is not on Windows 10. — [MS Learn: Windows 11 APIs for APOs](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/windows-11-apis-for-audio-processing-objects)
- No official user-mode "create a virtual microphone" API was found. Developers on OSR note that most resources focus on kernel-mode drivers. Commercial vendors still ship root-enumerated kernel virtual-mic drivers for Windows 11, and users report install failures with some of them (AudioRelay). — [OSR community](https://community.osr.com/t/seeking-assistance-how-to-create-virtual-input-and-output-devices-in-windows-11/59143); [AudioRelay community](https://community.audiorelay.net/t/virtual-mic-driver-does-not-install/1482)

### Inferences
- Current latency budget, estimated rather than measured: capture period (about 10 ms) + framer (up to 10 ms) + ring B at half of 8 frames (about 40 ms) + render period (about 10 ms) + VB-Cable internal fill (variable, up to about 70 ms by the staff statement) + the consuming app's own capture buffer (Discord/Zoom, typically 10-20 ms). Ring B and VB-Cable are the two largest app-adjacent terms.
- Quick win without a driver: lower ring B's target fill. Today it is 4 of 8 frames; try 1.5-2 frames, about 15-20 ms, with headroom for render-period jitter. This works only if the PI loop is low-bandwidth and the render thread is reliably scheduled. Measure underruns via the `GetCurrentPadding` history.
- A self-written virtual-mic driver removes the double buffering of "render endpoint -> cable -> capture endpoint" in a third-party driver. It gives VoiceCleaner control of the capture endpoint's period and lets it declare 128-240 frame support. It also removes the VB-Cable install and licensing dependency. Costs: an EV certificate (typically a few hundred USD per year; price not verified here), Partner Center registration, kernel-driver bugcheck risk, and a per-release attestation submission. HLK is not required for attestation, but there is no Windows Update distribution.
- An APO route (capture MFX/SFX on the physical mic) would avoid the virtual device entirely. But APOs bind to a specific device's driver package and are aimed at OEMs/IHVs, with HLK and CAPX on Windows 11, so it is impractical for arbitrary user mics.

### Gaps
- No primary documentation was found for VB-Cable's latency model; the official settings document cited in the forum was not located. No independent measurement of VB-Cable end-to-end delay was found.
- No current cost figures for EV certificates were verified. No 2025-2026 Microsoft API for user-mode virtual audio endpoints was found; the absence is noted, not confirmed.
- How commercial products (NVIDIA Broadcast, Krisp) implement their virtual devices was not verified.

## 3. Clock drift / adaptive resampling

### Takeaway
The best-documented designs control a very slow, smoothed resampling ratio from a filtered delay error. Adriaensen's zita-a2j/j2a uses a 2nd-order prefilter plus a 2nd-order loop filter with about 0.05 Hz bandwidth in normal operation and a wider bandwidth for the first 4 s. They feed a bandlimited polyphase-sinc resampler, not a polynomial interpolator. Windows also has a built-in alternative: `AUDCLNT_STREAMFLAGS_RATEADJUST` + `IAudioClockAdjustment::SetSampleRate` on a shared render stream, which lets the engine's SRC do the variable-ratio work. Catmull-Rom is likely acceptable for speech at a ratio of about 1 ± 150 ppm, but it is measurably worse than sinc. The bigger quality risk is jitter in the control signal, not the interpolator.

### Cited Findings
- Adriaensen, "Controlling adaptive resampling": the hard part is controlling the ratio, not resampling. Monitoring the raw buffer fill "won't work" directly because it jumps per period and isn't reliably observable. High-frequency components in ratio variation act like clock jitter and produce "parasitic signals, noise or distortion". The latency should be "stable and repeatable". — [Adriaensen, adapt-resamp.pdf](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)
- The zita design: a DLL timestamps each side's periods to give smooth continuous time. The error goes through a 2nd-order lowpass (bandwidth 20x the loop's), then a 2nd-order loop filter (as in JACK's DLL), and the resampler adds another lowpass on ratio changes. Normal loop bandwidth is "around 0.05 Hz", with a higher bandwidth for the first 4 seconds. — [Adriaensen, adapt-resamp.pdf](https://kokkinizita.linuxaudio.org/papers/adapt-resamp.pdf)
- PipeWire: streams, sources and sinks contain "a high quality adaptive resampler. It uses sinc based resampling with linear interpolation of filter banks". `resample.quality` ranges from 0 to 14 with a default of 4. The session manager prefers sources as graph drivers because "adaptive resampling should be done on the sinks rather than the source to avoid signal distortion when capturing audio". — [PipeWire props(7)](https://docs.pipewire.org/page_man_pipewire-props_7.html)
- PipeWire's `spa_io_rate_match`: the node sets a rate correction, "usually derived from a DLL or other adaptive mechanism that drives the node's buffer fill level toward a specific target". The resampler delay, including a fractional part, varies per cycle. — [PipeWire spa_io_rate_match](https://docs.pipewire.org/structspa__io__rate__match.html)
- libsamplerate: SINC_BEST gives 97 dB SNR at 97% bandwidth, SINC_MEDIUM 97 dB at 90%, SINC_FASTEST 97 dB at 80%. LINEAR and ZOH "quality is poor" and are not bandlimited. — [libsamplerate API](https://libsndfile.github.io/libsamplerate/api_misc.html)
- speexdsp resampler: quality 0-10. "A quality of 3 is acceptable for most desktop uses"; quality 0 is "certainly better than using linear interpolation resampling". Higher quality means more latency and complexity. — [Speex manual](https://www.speex.org/docs/manual/speex-manual/node7.html)
- Windows: `AUDCLNT_STREAMFLAGS_RATEADJUST` gives `IAudioClockAdjustment::SetSampleRate`, which is valid only for shared-mode render streams. `AUDCLNT_STREAMFLAGS_AUTOCONVERTPCM` inserts a channel matrixer and SRC. `AUDCLNT_STREAMFLAGS_SRC_DEFAULT_QUALITY` selects a better SRC and is recommended when the audio is "ultimately intended to be heard by humans". — [MS Learn: AUDCLNT_STREAMFLAGS](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants)

### Inferences
- VoiceCleaner's structure (resampler between the capture domain and the render domain, PI loop on ring-B fill) matches the PipeWire/zita topology. Two upgrades follow from the sources:
  1. Low-pass the fill measurement before the PI. Sample ring-B occupancy at a consistent point, such as right after each render-thread write, plus `GetCurrentPadding`, or time-interpolate it with QPC timestamps from `GetBuffer`'s `pu64QPCPosition`. Then filter it, with loop bandwidth around 0.05-0.1 Hz once locked and a fast-acquire phase for the first few seconds.
  2. Slew-limit or smooth the ratio inside the resampler.
- On Catmull-Rom (cubic Hermite) at a ratio of about 1.0: there is no meaningful imaging or aliasing from a rate change, because input and output rates differ by 150 ppm or less. The error is the interpolator's fractional-delay frequency response: high-frequency roll-off and phase error that vary with the fractional position. As the fractional phase sweeps slowly, this becomes a slow, small modulation of the top octave (about 8-24 kHz), mostly above speech's critical band, and VoIP codecs downstream usually band-limit anyway (Opus wideband/fullband). For speech it is very likely inaudible. A speexdsp-quality-3-class or libsamplerate SINC_FASTEST resampler would remove the concern at a small CPU cost. This is analysis only; no measurement source was found.
- Alternative: drop the custom resampler and open the VB-Cable render stream with `AUDCLNT_STREAMFLAGS_RATEADJUST`, then call `IAudioClockAdjustment::SetSampleRate(48000*(1+e))` from the PI output. This offloads SRC to audiodg. The quality of that SRC is undocumented.
- With a self-owned virtual driver, the virtual endpoint could be slaved to the capture device's clock, as VAC's "clock control" does. That would remove drift compensation entirely.

### Gaps
- No published spec of the Windows engine SRC quality (default vs. `SRC_DEFAULT_QUALITY`) was found.
- No measurement source compares cubic Hermite vs. sinc for speech at ratios near 1.

## 4. Device changes, invalidation, sample-rate mismatches

### Takeaway
WASAPI apps must do their own "stream routing". On `AUDCLNT_E_DEVICE_INVALIDATED`, release all interfaces and reactivate, either on the same device ID or the new default. Listen to `IMMNotificationClient` (non-blocking callbacks only) and `IAudioSessionEvents::OnSessionDisconnected`. Supporting 44.1 kHz or other endpoints is easy: either use `AUTOCONVERTPCM | SRC_DEFAULT_QUALITY` in `IAudioClient::Initialize`, or resample internally, instead of refusing.

### Cited Findings
- Apps using MMDeviceAPI or WASAPI directly must implement stream routing themselves: handle default-device change, device removal/addition, and format change. Media Foundation, DirectSound and WAVE do this automatically. — [MS Learn: Stream Routing](https://learn.microsoft.com/en-us/windows/win32/coreaudio/stream-routing)
- Recovery from `AUDCLNT_E_DEVICE_INVALIDATED` for default-device apps: release `IAudioClient` and every other WASAPI interface, call `GetDefaultAudioEndpoint`, and activate again. For a specific device: release, reactivate on the same device, and prompt the user only if that fails. `IAudioSessionEvents::OnSessionDisconnected` gives the reason (removed, service shut down, format changed, and so on). — [MS Learn: Recovering from an Invalid-Device Error](https://learn.microsoft.com/en-us/windows/win32/coreaudio/recovering-from-an-invalid-device-error)
- `IMMNotificationClient` rules: methods must be non-blocking and never wait on a sync object; never call Register/UnregisterEndpointNotificationCallback inside a callback; never release the final reference on an MMDevice object in a callback. — [MS Learn: IMMNotificationClient](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient)
- `AUTOCONVERTPCM` plus `SRC_DEFAULT_QUALITY` lets a shared stream use a format other than the mix format (for example, the app stays at 48 kHz on a 44.1 kHz endpoint). — [MS Learn: AUDCLNT_STREAMFLAGS](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants)
- `InitializeSharedAudioStream` can fail with `AUDCLNT_E_ENDPOINT_CREATE_FAILED` (unplugged or reconfigured) or `AUDCLNT_E_RESOURCES_INVALIDATED` (suspended stream and similar cases). — [MS Learn: InitializeSharedAudioStream](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclient3-initializesharedaudiostream)

### Inferences
- Pattern for VoiceCleaner:
  - The `IMMNotificationClient` callback only posts a message to a control thread, using an atomic flag plus `SetEvent`.
  - The capture and render threads treat any `AUDCLNT_E_DEVICE_INVALIDATED` from `GetBuffer`/`ReleaseBuffer`/`GetCurrentPadding` as "stop and request rebuild".
  - The control thread tears down and rebuilds that side only: the capture side on mic change, the render side on cable change. It keeps the DSP state and refills ring B to target, so the other side keeps running and only a short gap appears.
  - Prefer the eCommunications default capture role if users switch headsets often. This is a design choice, not sourced.
- Instead of requiring 48 kHz on both endpoints:
  - Capture: initialize with the 48 kHz float format plus `AUTOCONVERTPCM | SRC_DEFAULT_QUALITY`, so the engine resamples a 44.1/96 kHz mic.
  - Render to the cable: same flags. Alternatively, run the internal resampler with a nominal ratio of fs_out/48000 and the PI correction on top. That is the same code path, generalized, and keeps drift handling in one place.

### Gaps
- No documented latency cost of engine-side `AUTOCONVERTPCM` SRC was found.

## 5. Acoustic echo cancellation

### Takeaway
AEC matters when the user listens on speakers: the far-end voice from Discord/Zoom re-enters the mic, and VoiceCleaner's virtual mic sits in front of those apps' own AEC. Their AEC usually still works when it can reference their own render stream, but nonlinear processing before it (denoising, gain) can degrade it; this is an inference. Windows options:
- Use the OS/OEM communications-mode AEC on capture (`AudioCategory_Communications`; Windows 11 Voice Clarity on supported builds).
- Use `IAcousticEchoCancellationControl` (Windows 11 build 22621+) to point the endpoint's AEC at the correct render device.
- Run WebRTC AEC3 or speexdsp AEC in-app, with a loopback capture of the speaker endpoint as reference.

### Cited Findings
- `IAcousticEchoCancellationControl::SetEchoCancellationRenderEndpoint` sets the render endpoint used as the AEC reference. You obtain it from `IAudioClient::GetService` after `Initialize`; `E_NOINTERFACE` means the endpoint's AEC (if any) doesn't allow control. Minimum client: Windows build 22621. — [MS Learn: IAcousticEchoCancellationControl](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nn-audioclient-iacousticechocancellationcontrol)
- Windows 11 AEC APO framework: the engine supplies the AEC APO a reference stream from "an appropriate render endpoint" and switches it when the render device changes. AEC APOs that use private driver channels "typically" work only with the integrated render device, not USB/Bluetooth. — [MS Learn: Windows 11 APIs for APOs](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/windows-11-apis-for-audio-processing-objects)
- Signal processing modes: Communications mode is where AEC/NS apply. Apps can query which effects (for example, AEC) apply to a stream. Raw capture must not include echo control. — [MS Learn: Audio signal processing modes](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/audio-signal-processing-modes)
- Windows 11 "Voice Clarity" uses low-complexity AI models to cancel echo, suppress noise and reduce reverberation. It is on by default for apps using Communications Signal Processing Mode and runs on x64/Arm64 CPUs without an NPU. These are secondary press sources (2024). — [Croma Unboxed](https://www.croma.com/unboxed/microsoft-windows-11-voice-clarity-feature); [2wtech](https://2wtech.com/windows-11-receives-ai-backed-voice-clarity)
- WebRTC AEC3 has a dedicated echo-path delay estimator (matched filters on a 4x-decimated render signal). It is built inside WebRTC's GN build, so extraction requires vendoring. — [WebRTC code review](https://codereview.webrtc.org/2644123002/patch/180001/190001)

### Inferences
- Recommended order for VoiceCleaner:
  1. Default: no AEC, but tell headset users nothing is needed. Detect speaker usage heuristically or via a user toggle.
  2. "Speaker mode": open capture with `AudioCategory_Communications` and without RAW, so the OEM or Windows (Voice Clarity) AEC runs before VoiceCleaner's DSP. On build 22621+, call `IAcousticEchoCancellationControl` to target the user's actual speaker endpoint. This costs no code beyond flags but adds OEM processing latency.
  3. In-app WebRTC AEC3: open a WASAPI loopback (`AUDCLNT_STREAMFLAGS_LOOPBACK`) on the default render endpoint as reference. This works everywhere but costs about 10-20 ms of extra alignment buffering plus CPU and build effort; this is an estimate.
- Running AEC before denoising is the standard order. Denoise-then-AEC breaks the AEC's linear echo-path model.

### Gaps
- No official Microsoft doc on Voice Clarity's developer surface was retrieved; the Learn URL tried returned a near-empty page. No measured latency of the communications-mode capture pipeline was found.

## 6. MMCSS, power throttling, hybrid CPUs

### Takeaway
Keep MMCSS ("Pro Audio"/"Audio") on the real-time threads; Windows 11 tags MMCSS threads with dedicated QoS levels. Explicitly opt the process and threads out of EcoQoS/execution-speed throttling with `SetProcessInformation`/`SetThreadInformation`, and opt out of timer-resolution throttling. Windows 11 may ignore timer-resolution requests from occluded or minimized processes that aren't audible, which matters for a tray app whose output goes to a virtual device. Prefer the Real-Time Work Queue for audio work items so the low-latency protection mode covers them.

### Cited Findings
- QoS on Windows 11: QoS influences core selection on heterogeneous CPUs. EcoQoS "Always selects most efficient CPU frequency and schedules to efficient cores". MMCSS tags audio threads with Media/Deadline QoS. "Processes which are determined to be playing audio are HighQoS." — [MS Learn: Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- `SetProcessInformation(ProcessPowerThrottling)`: with ControlMask `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` and StateMask 0 the process is opted out (HighQoS); otherwise the system infers QoS heuristically. `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` controls timer handling: "By default in Windows 11 if a window owning process becomes fully occluded, minimized, or otherwise non-visible to the end user, and non-audible, Windows may automatically ignore the timer resolution request". `SetThreadInformation(ThreadPowerThrottling)` does the same per thread. — [MS Learn: SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation); [MS Learn: Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- MMCSS: tasks are registered under `HKLM\...\Multimedia\SystemProfile\Tasks` (Audio, Pro Audio, and others). `SystemResponsiveness` reserves CPU for low-priority tasks (default 20%; 100 disables MMCSS). Threads join with `AvSetMmThreadCharacteristics`. — [MS Learn: MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)
- Steinberg says Windows 10 limits MMCSS real-time threads to 32 per process. This is a vendor note, not a Microsoft source. — [Steinberg help](https://www.steinberg.help/r/windows-10-audio-dropouts-on-multi-core-cpu-setups)
- Low-latency protection covers RTWQ/MF work queues tagged Audio/ProAudio rather than arbitrary app threads. — [MS Learn: Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)
- Anecdotal: on Windows 11 hybrid laptops, minimized or background programs ran only on E-cores. — [MS Q&A](https://learn.microsoft.com/en-us/answers/questions/1027852/windows-11-22h2-thread-director-issues-with-intel)

### Inferences
- At startup, VoiceCleaner should:
  1. Call `SetProcessInformation(ProcessPowerThrottling, {CURRENT_VERSION, ControlMask = EXECUTION_SPEED | IGNORE_TIMER_RESOLUTION, StateMask = 0})`.
  2. On each audio thread, call `SetThreadInformation(ThreadPowerThrottling, {ControlMask = THREAD_POWER_THROTTLING_EXECUTION_SPEED, StateMask = 0})`.
  3. Keep `AvSetMmThreadCharacteristicsW(L"Pro Audio")` + `AvSetMmThreadPriority(AVRT_PRIORITY_CRITICAL)`. Keep it to 3 threads.
- Its output goes to a virtual cable. The QoS doc says audio-playing processes are classed HighQoS, but it does not say whether rendering to a virtual endpoint counts as "audible"; the explicit opt-out removes that uncertainty.
- Event-driven WASAPI does not depend on timer resolution. Only `Sleep`/`WaitForSingleObject` timeouts in fallback paths do, so `timeBeginPeriod` is unnecessary if all waits are event-driven.
- Optionally move the relay/DSP work onto an RTWQ shared "Pro Audio" queue (`RtwqLockSharedWorkQueue(L"Pro Audio", ...)`, `RtwqPutWaitingWorkItem` on the WASAPI event). This is the Microsoft-recommended way to be covered by low-latency protection mode; it matters most if small periods are adopted.
- Avoid hard affinity pinning to P-cores. Rely on MMCSS plus HighQoS. Affinity can be exposed via the MMCSS registry, but that is system-wide.

### Gaps
- No Microsoft documentation was found that explicitly states MMCSS threads are never scheduled on E-cores. No measurements were found of MMCSS behavior on Intel hybrid or Snapdragon X under Windows 11 24H2/25H2.
